## 1. 루프 엔지니어링(Loop Engineering) 개요

### 1.1 정의
루프 엔지니어링은 단순히 LLM에 도구를 제공하고 실행하는 단발성 호출(Single-turn)을 넘어, **에이전트가 스스로 실행하고, 관찰하며, 수정하고, 검증하는 반복 루프를 체계적으로 설계하고 제어하는 기술**입니다. 이는 에이전트의 자율성(Autonomy)과 신뢰성(Reliability)을 보장하는 핵심 기반이 됩니다.

### 1.2 단발성 호출(Single-turn)로부터의 진화
초기 LLM 애플리케이션은 단발성 프롬프팅이나 단순한 Chain-of-Thought(CoT)에 의존했습니다. 이는 프롬프트 포맷에 매우 민감하고 환각(Hallucination)에 취약했습니다. 루프 엔지니어링은 에이전트에게 환경(컴파일러, 파일 시스템, API 등)과 상호작용할 수 있는 도구를 부여하고, 그 실행 결과를 관찰하여 스스로 오류를 수정해 나가는 피드백 루프를 구축함으로써 에이전트의 실질적인 문제 해결 능력을 극대화했습니다.

## 2. 루프 엔지니어링의 핵심 철학

`jeo`는 다음 4+1 프로젝트의 철학을 융합하여 경량 JSON-루프 에이전트 노선을 확립했습니다.

| 프로젝트 | 핵심 철학 | JEO가 계승한 가치 |
| :--- | :--- | :--- |
| **pi-mono** (Zechner) | **미니멀 코어**: "코어에 더한 기능만큼 모델의 자유 추론 능력이 저하된다." 도구 수 최소화 및 프롬프트 경량화(<1K 토큰). | 코어 비대화 거부. 무거운 기능은 스킬(`SKILL.md`)이나 외부 CLI로 위임. |
| **nullclaw** (Zig) | **최소주의**: "가능한 한 적게, 필요한 만큼만." 단일 파일 구현 및 의존성 제로. | Bun 순수 TypeScript 환경 유지, 외부 의존성 배제. |
| **zeroclaw** (Rust) | **로컬 주권 & 크래시 내성**: "전원을 뽑아도 멈출 뿐, 다른 시스템을 깨뜨리지 않는다." | 모든 상태는 `.jeo/` 로컬에 저장하며, 임시 파일 쓰기 후 이름 변경(temp-write + rename) 방식을 통해 원자적 상태 관리 보장. |
| **hermes** (Nous) | **경험-스킬 증류**: 세션 종료 시 획득한 경험을 재사용 가능한 스킬로 자동 추출하여 세션 간 누적 학습 실현. | 세션 종료 시 `.jeo/memory/MEMORY.md`에 로컬 증류(1회 요약 호출)를 수행하고 다음 세션에 주입. |
| **gjc** (계승 대상) | **Staff Engineer 규율**: 검증 없는 완료(`done`) 금지, 편집 무결성 보장(hashline), 명확한 능력 경계 설정. | **done 검증 가드** 및 **hashline-lite 편집 앵커** 도입. |

## 3. 루프 엔지니어링의 주요 장점

1. **결과물의 높은 신뢰성 (Correctness)**
   - 에이전트가 코드를 작성한 후 반드시 테스트나 컴파일을 실행하도록 강제함으로써, 구문 오류나 논리적 결함이 있는 상태로 작업을 종료하는 것을 원천 차단합니다.
2. **모델 오작동 및 비용 낭비 방지 (Resilience)**
   - 동일 도구 반복 호출(Repeat), 무한 루프(Cycle), 연속 실패(Consecutive Failure) 등을 감지하는 가드 메커니즘을 통해 API 비용 낭비를 막고 에이전트가 스스로 탈출구를 찾도록 유도합니다.
3. **컨텍스트 효율성 (Context Efficiency)**
   - 실행 이력이 길어질 때 중요 정보(수정된 파일 목록 등)를 보존하면서 이전 도구 출력을 동적으로 축소(Compaction)하여, 모델의 컨텍스트 윈도우 부하를 줄이고 추론 품질을 유지합니다.
4. **지연 시간 단축 (Latency Reduction)**
   - 독립적인 파일 쓰기/수정 작업을 병렬로 배치 처리하고, 포스트 턴 훅(Post-turn Hook)을 배치 단위로 1회만 실행하여 전체 실행 속도를 높입니다.

## 4. JEO의 현재 루프 아키텍처 분석

- **메인 루프 엔진 (`src/agent/loop.ts` & `engine.ts`)**
  - 에이전트의 메인 실행 루프로, 모델 호출 -> 도구 파싱 -> 도구 배치 실행 -> 포스트 턴 훅 실행 -> 상태 업데이트의 주기를 관리합니다.
- **루프 가드 메커니즘 (`src/agent/loop-guards.ts`)**
  - gjc의 중간 판단 로직을 계승하여 `GuardState` 택소노미를 정의하고, 반복 힌트 제공 및 `done` 검증 가드 평결(`classifyDoneGate`)을 순수 함수로 분리하여 관리합니다. 변이 도구 사용 후 검증 신호가 없거나 훅 진단 실패 시 `done` 호출을 1회 차단합니다.
- **로컬 메모리 증류 (`src/agent/memory.ts`)**
  - 세션 종료 시 로컬 메모리를 증류하고, BM25(lexical)와 그래프 인접도(graph proximity)를 결합한 하이브리드 리랭커를 통해 임베딩 없이도 고성능 메모리 검색을 수행합니다.

## 5. JEO 성능 개선을 위한 제안 방향

현재의 견고한 게이트 및 가드 시스템 위에 추가적인 성능 향상과 효율성 극대화를 위해 다음과 같은 개선 방향을 제안합니다.

### 5.1 LSP-lite (AST 기반 사전 검증 도입)
- **개념**: 파일 수정 즉시 메모리 상에서 구문 오류(Syntax Error)를 1차 검증하는 경량 파서 레이어입니다.
- **구현 방안**: Bun 내장 API 또는 가벼운 zero-dependency AST 파서를 활용하여 에디터 도구 내에 통합합니다.
- **기대 효과**: 컴파일 오류가 있는 편집을 즉각 거부하고 모델에 피드백을 주어, 무거운 bash 실행 횟수를 줄이고 스텝 버짓을 절약합니다.

### 5.2 3-Way Merge 기반 에디터 복구 (Conflict Resolution)
- **개념**: 파일이 크게 변경되었거나 충돌이 발생했을 때 편집을 거부하는 대신 자동으로 병합하는 알고리즘입니다.
- **구현 방안**: 에디터 도구 내에 단순한 3-Way Merge 알고리즘(또는 diff3 스타일의 라인 매칭)을 구현합니다.
- **기대 효과**: 모델이 오래된(stale) 파일 상태를 기준으로 편집을 시도하더라도 사소한 차이는 자동으로 병합하여 편집 성공률을 극대화합니다.

### 5.3 세밀한 도구 병렬화 (Disjoint File Concurrency)
- **개념**: 서로 겹치지 않는 파일들에 대한 읽기/쓰기 작업을 동시에 실행하는 병렬화 기법입니다.
- **구현 방안**: 도구 배치 내에서 대상 파일 경로를 정규화하여 분석한 뒤, 독립적인 파일들에 대한 읽기와 쓰기 작업을 동일 그룹으로 묶어 병렬로 실행합니다.
- **기대 효과**: 다중 파일 분석 및 수정 작업이 빈번한 대형 태스크에서 턴당 실행 지연 시간(Latency)을 추가로 단축합니다.

### 5.4 SQLite FTS5 기반 로컬 메모리 검색 고도화
- **개념**: Bun 내장 SQLite의 FTS5(Full-Text Search) 모듈을 활용한 고속 로컬 메모리 검색 엔진입니다.
- **구현 방안**: `.jeo/memory/` 내의 데이터를 SQLite FTS5 가상 테이블로 인덱싱하여 검색을 수행합니다.
- **기대 효과**: 외부 의존성 제로(zero-dependency) 원칙을 지키면서도 대용량 메모리 세션에서 검색 속도와 정확도를 대폭 향상시킵니다.

### 5.5 비동기/Detached 서브에이전트 병렬 실행 지원
- **개념**: 의존 관계가 없는 독립적인 태스크들을 서로 다른 서브에이전트에 할당하여 백그라운드에서 병렬로 실행하는 아키텍처입니다.
- **구현 방안**: `jeo team` 엔진에 비동기 태스크 큐 및 워커 풀 개념을 도입하여 병렬 실행 후 결과를 취합합니다.
- **기대 효과**: 멀티코어 환경을 활용하여 대규모 리팩토링이나 다중 모듈 개발 시 전체 워크플로 완료 시간을 획기적으로 줄입니다.
